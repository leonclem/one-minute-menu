# Internal A/B/C object-edit spike harness

This change adds an internal-only experiment harness for comparing object-removal and relocation prompts across NB2 and NB Pro. It validates a versioned scenario manifest, renders the production Image A/Image B pair, derives A/B/C instructions from the production composer, and can upload hashed artifacts to the existing Studio bucket. Execution defaults to dry-run; live calls require an environment gate, a confirmation token, an owner UUID, and a bounded selected set. **Watch for:** **confirmed** — the manifest admits cohorts larger than the specified ten cases; **confirmed** — failed dry-run construction bypasses filters; **confirmed** — valid long case IDs make post-generation artifact upload fail; and **confirmed** — the configurable artifact owner can target a customer storage namespace.

**Verdict**: NEEDS_CHANGES

## High-level view

The manifest closes tags to the six allowed values and checks every operation/model cohort for coverage, but it enforces a minimum of ten cases rather than the requested fixed cohort size. That leaves the comparison population mutable while still passing validation.

Dry-run treats a construction failure as a synthetic A request before selection is applied. A filtered dry-run can therefore report an execution that was never selected and can hit its cap unexpectedly.

The generated artifact label is longer than the upload schema permits for valid manifest IDs, and the caller-controlled owner UUID can direct service-role writes into a customer path.

No tests cover the new manifest, construction, artifact, or runner modules. TypeScript compilation verifies the integration surface, but these deterministic boundary cases remain unverified.

<details>
<summary>Details</summary>

## Cohort cardinality remains open despite closed tags

`StudioObjectEditSpikeManifestZ` requires at least 40 cases and each `(operation, requestedModelClass)` group to contain at least ten cases. A 41-case manifest, or a group with eleven cases, parses successfully. The request calls for ten cases per remove/move × NB2/NB Pro group, so this is a **confirmed** comparison-control gap: adding cases changes the aggregate evidence population without a schema failure. Require exactly ten cases in each group and exactly 40 cases overall, while preserving the existing per-group six-tag coverage check.

## Construction failures evade dry-run filters

`runStudioObjectEditSpike` constructs an A/B/C group before evaluating `selectRequests`. When construction throws in dry-run mode, its catch block always appends a synthetic variant-A entry to `selected`. This is a **confirmed** filtering and bound violation: a run filtered to variant C, different scenario tags, or another case can still contain the failed case’s A record, and `assertExecutionBound` counts it. Preserve a separate validation-failure record only after applying case-level filters and the requested variants, or reject invalid selected input before collecting requests.

## Live artifact retention fails for valid manifest identifiers

Scenario IDs may be 100 characters long. `outputArtifactUpload` builds `case-${caseId}-${variant}`, which reaches 107 characters, while `SpikeArtifactUploadInputZ.label` accepts at most 80. This is a **confirmed** live failure after the provider has returned an image: `uploadSpikeArtifact` rejects the label, the catch converts the result to `transport_error`, and the output has no retained artifact. Use a short stable label, for example a variant plus a digest of the case ID, or reduce the manifest ID maximum to a compatible bound.

## Service-role artifact writes are not limited to the internal namespace

`artifactStorageOwnerUserId` is an arbitrary UUID supplied by the runner configuration; `buildStudioStoragePath` then writes to `${owner}/studio/...` with the service-role client. This is a **confirmed** trust-boundary gap because the documented internal owner is not enforced and any known customer UUID can be supplied by an internal caller. Resolve the owner from a non-request configuration value, or validate it against an explicit internal identity before creating the storage path.

## Harness behavior has no direct regression coverage

The repository contains no tests referencing `parseStudioObjectEditSpikeManifest`, `constructSpikeComparisonGroup`, `uploadSpikeArtifact`, or `runStudioObjectEditSpike`. This is a **confirmed** coverage gap for the exact-ten validation, invariant rejection, dry-run selection behavior, live interlocks, and artifact naming boundary. Add focused unit tests with mocked storage and mutation execution; no provider call is needed.
